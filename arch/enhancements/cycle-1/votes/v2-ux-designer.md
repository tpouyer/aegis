# Votes: UX Designer

## growth-contextual-empty-states.md
- **Verdict**: APPROVE
- **Reasoning**: This is the single most impactful UX fix in the entire cycle. The current experience -- loading spinners that never resolve, raw error messages like "Failed to load board" -- is a first-session deal-breaker. Every dead-end screen without a clear next action is a user lost. The proposal correctly identifies that empty states are not just filler; they are onboarding touchpoints. The suggested copy, CTAs, and progressive guidance (setup checklist in Settings) follow established patterns from Linear and GitHub Projects that users already understand.
- **Conditions**: (1) All empty state components must meet WCAG 2.1 AA: CTAs must have sufficient color contrast, focus indicators, and screen-reader-accessible labels. (2) Copy must be tested with at least 2-3 real outside contributors before finalizing -- wording that resonates with internal Red Hat engineers may not land the same way with OSS contributors. (3) Illustrations or icons should be lightweight SVGs, not heavy images that delay rendering.

## growth-interactive-playground.md
- **Verdict**: APPROVE
- **Reasoning**: A try-before-you-buy experience is the gold standard for developer tool adoption. The current landing page asks users to hand over GitHub credentials before they have any understanding of what Aegis does, which is a massive trust barrier. The playground directly solves this by letting users interact with real UI components using static data. The proposal is well-scoped: it reuses existing BoardView, ChatView, and IDELayout with injected fixture data rather than duplicating UI code.
- **Conditions**: (1) The persistent "You are viewing sample data" banner must be visually distinct and impossible to miss -- use a contrasting background color (e.g., amber/yellow) and ensure it does not overlap or obscure the content below it. Screen readers must announce it. (2) Sample data must feel realistic but never include real issue keys, real names, or any data that could be mistaken for production content. (3) The disabled chat input must clearly communicate WHY it is disabled ("Connect an LLM provider to start chatting"), not just appear broken. A grayed-out input with no explanation is a poor pattern.

## growth-keyboard-shortcuts-command-palette.md
- **Verdict**: REJECT
- **Reasoning**: This proposal is a near-duplicate of three other proposals in the same cycle: power-command-palette.md, power-keyboard-shortcuts.md, and power-ide-file-search.md. All four propose the same command palette (Cmd+K), the same global shortcuts, the same board navigation (j/k/h/l), and the same IDE shortcuts. Approving this alongside the others would create confusion about which spec to implement. The power-user variants are better scoped -- they separate the command palette, keyboard shortcuts, and file search into distinct, independently deliverable pieces with clearer technical sketches.
- **Conditions**: N/A. Recommend consolidating any unique elements from this proposal (if any) into the three power-user proposals.

## growth-progressive-auth-nudges.md
- **Verdict**: APPROVE
- **Reasoning**: The current ProviderPicker modal is the worst UX moment in Aegis. A new user opens AI Chat, eager to try the product's core feature, and is immediately blocked by a modal dialog with no context, no recommendations, and no explanation of costs. The inline provider setup pattern proposed here -- a card within the chat message area with clear provider comparisons and Ollama auto-detection -- is dramatically better. Keeping the user in-context during auth setup (no modal, no page navigation) reduces cognitive load and preserves the user's sense of progress. The auth redirect preservation pattern is also overdue -- losing the user's intended destination after OAuth is a basic UX failure that this proposal corrects.
- **Conditions**: (1) The Ollama auto-detection fetch to localhost:11434 must fail completely silently with no console errors, no flicker, and no layout shift if Ollama is not running. (2) Provider recommendation cards must be keyboard-navigable and screen-reader-accessible with clear role and aria-label attributes. (3) The "welcome toast" replacement for the OnboardingWizard should use an 8-second auto-dismiss, but must also dismiss on Escape key and provide a manual close button -- auto-dismiss-only toasts are an accessibility anti-pattern.

## growth-shareable-deep-links.md
- **Verdict**: APPROVE
- **Reasoning**: Encoding contextual state in URLs is fundamental web UX that Aegis currently lacks. The fact that board filters, chat message positions, and IDE file selections are not reflected in the URL means users cannot bookmark their work, share context with teammates, or use browser back/forward navigation meaningfully. The proposal addresses all three views with simple, human-readable URL parameters that follow existing conventions (search params for filters, hash anchors for chat messages, query params for file+line). The "Copy link" action on chat messages is a particularly strong interaction pattern for viral sharing.
- **Conditions**: (1) URL changes from filter adjustments must use `replaceState` (not `pushState`) to avoid polluting browser history with every filter toggle. The proposal does not specify this. (2) The chat message highlight animation on scroll-to must be subtle (e.g., a brief yellow pulse that fades) and must respect prefers-reduced-motion for users who have disabled animations. (3) The auth-gated fallback must show a clear, informative preview of what the link points to -- not just "Sign in to view" but "Sign in to view AAP-1234: Fix API pagination in job_templates.py, line 42."

## platform-cache-eviction-and-quota.md
- **Verdict**: APPROVE
- **Reasoning**: While this is primarily a platform concern, it has direct UX consequences. Silent data loss when storage quota is exceeded, or degraded performance from bloated caches, directly impacts the user experience. The Settings page storage panel is a good addition that gives power users visibility and control. The "Storage full -- some data may load slower" toast is appropriate for graceful degradation.
- **Conditions**: (1) The storage panel in Settings must use clear, non-technical language: "Chat history: 45 MB" not "aegis-chat IndexedDB: 47,185,920 bytes." (2) "Clear cache" buttons must have confirmation dialogs -- one misclick should not wipe hours of chat history. (3) The emergency eviction toast must be persistent (not auto-dismiss) so users understand why performance may change.

## platform-llm-context-budget.md
- **Verdict**: APPROVE
- **Reasoning**: Context window overflow is one of the most confusing failure modes in AI chat -- the user sends a message and gets back garbage, an error, or silence, with no understanding of why. The token budget progress bar gives users visibility into a previously invisible constraint. The compaction notifications ("Older messages were summarized") set correct expectations. This directly improves the user's mental model of the AI system.
- **Conditions**: (1) The context usage indicator must be unobtrusive -- a thin progress bar or small text in the chat header, not a prominent element that distracts from the conversation. Consider showing it only when usage exceeds 50%. (2) Compacted/summarized messages must be visually distinct but not alarming -- use a subtle background tint and a small "summarized" label, not a warning icon. (3) The hard-truncation toast ("Older messages were removed") must explain what happened in plain language and offer a way to start a fresh conversation if the user prefers.

## platform-offline-resilience.md
- **Verdict**: APPROVE
- **Reasoning**: The online/offline indicator and the "Pending changes" panel are excellent UX additions. Users currently have zero visibility into connectivity state until something fails, which is disorienting. The three-state indicator (green/yellow/red) with queued mutation badge follows the Figma/Slack pattern that users already understand. The mutation queue with manual retry/discard gives users control over their queued work rather than leaving them guessing.
- **Conditions**: (1) The offline indicator must be visible but not intrusive -- a small dot in the header is appropriate, not a full-width banner. The "Offline" label should only appear alongside the red dot, not as a standalone element that takes up space. (2) The "Pending changes" panel must clearly show what each queued mutation will do in plain language ("Move AAP-1234 to In Progress") not technical payload descriptions. (3) Optimistic updates that persist across page reloads must be visually flagged (e.g., a subtle dashed border on the card) so users know which board state is unconfirmed.

## platform-resilient-api-fetch.md
- **Verdict**: APPROVE
- **Reasoning**: While this is primarily infrastructure, the UX improvement is real: users currently see jarring optimistic-UI rollbacks and error toasts when transient API failures occur. Automatic retry with backoff eliminates the vast majority of these surface-level disruptions. The optional "rate limited -- requests queued" indicator is a thoughtful touch that keeps users informed without alarming them.
- **Conditions**: (1) The throttle indicator, if implemented, should use amber/yellow styling (not red) to convey "slowed down" rather than "broken." (2) During retry, the UI must not appear frozen -- if a board refresh is retrying, the refresh button should show its spinning animation and not reset between retries.

## platform-structured-error-recovery.md
- **Verdict**: APPROVE
- **Reasoning**: The current error handling is genuinely hostile to users: raw technical error messages in toasts that auto-dismiss after 5 seconds, giving the user no time to read, understand, or act. The error classification with per-category recovery actions transforms errors from dead-ends into guided recovery moments. The persistent auth-expired banner with one-click re-authentication is exactly what users expect from modern web apps. The error history panel (bell icon with badge) ensures users never lose track of what went wrong.
- **Conditions**: (1) Error toasts with action buttons must not auto-dismiss -- the proposal specifies this for AUTH_EXPIRED and NETWORK but should extend it to any toast with an action button. Users need time to read and decide. (2) The error history panel must be keyboard-accessible (focusable, navigable with arrow keys, action buttons reachable via Tab). (3) Recovery action labels must use plain verbs: "Sign in again" not "Re-authenticate", "Try again" not "Retry request." Avoid technical jargon in user-facing error messaging.

## power-command-palette.md
- **Verdict**: APPROVE
- **Reasoning**: The command palette is the single most expected missing feature for Aegis's developer audience. Every developer tool in the competitive landscape has one. The three-mode design (issue search, file search with `>` prefix, command mode with `/` prefix) is intuitive and mirrors the VS Code / Linear conventions that the target audience already knows. The recency-based result boosting ensures the palette becomes more useful over time. This will be the primary navigation mechanism for power users within days of adoption.
- **Conditions**: (1) The palette must trap focus when open: Tab and Shift+Tab must cycle within the dialog, not escape to the page behind it. Escape must close it. This is a baseline accessibility requirement for modal overlays. (2) The fuzzy match must be generous -- typos and partial matches should surface results. Prioritize recall over precision in the ranking algorithm. (3) When no results match, show a clear "No results for [query]" message rather than an empty list, and suggest alternative modes ("Try searching files with > or commands with /").

## power-ide-file-search.md
- **Verdict**: APPROVE
- **Reasoning**: File navigation via folder-by-folder expansion in the FileExplorer is the biggest usability bottleneck in the IDE. For a repo with deep directory nesting (4+ levels), finding a file takes 8-10 clicks. Cmd+P fuzzy file search reduces this to ~3 keystrokes. This is the most natural and expected interaction pattern in any IDE, and its absence makes Aegis's IDE feel incomplete. The Go-To-Symbol and Go-To-Line features are near-free wins since they delegate to Monaco's built-in capabilities.
- **Conditions**: (1) The file finder overlay must be visually distinct from the command palette to avoid user confusion about which mode they are in. Either share the same component with a clear mode indicator (e.g., "Files" label in the search bar) or use a visually differentiated overlay. (2) Path display in results should show the relative path with the matching segments highlighted (bold or underlined), not just the filename. (3) The overlay must render quickly even on large repos -- defer rendering of off-screen results to avoid jank.

## power-keyboard-shortcuts.md
- **Verdict**: APPROVE
- **Reasoning**: Context-aware keyboard shortcuts are table-stakes for the developer audience. The layered scoping approach (global, board, chat, IDE) is the correct architecture -- it prevents shortcut collisions across views and matches how VS Code and Linear handle context-dependent keybindings. The board shortcuts (j/k for card navigation, Enter to open, c for chat, e for IDE) bring Aegis in line with Jira's own keyboard navigation that Red Hat engineers already have in muscle memory. The `?` help overlay is essential for discoverability.
- **Conditions**: (1) Single-key shortcuts (j, k, c, e, etc.) must be suppressed when any text input, textarea, or contenteditable element has focus. The proposal mentions this but it must be tested rigorously -- a missed guard here would make typing in the filter bar or chat input impossible. (2) The focused card must have a clearly visible focus ring that meets WCAG 2.1 AA contrast requirements (3:1 minimum against adjacent colors). (3) Cmd+W for closing IDE tabs is dangerous -- it conflicts with the browser's "close tab" shortcut. This specific binding should be reconsidered or only activated when Monaco has focus.

## power-quick-issue-actions.md
- **Verdict**: APPROVE
- **Reasoning**: The right-click context menu and multi-select batch operations directly address the excessive click count for common board operations. A scrum lead triaging 20 issues should not need 80+ clicks. The context menu pattern (right-click or Space on focused card) is familiar from file managers, IDEs, and Linear. Multi-select with Cmd+click and Shift+click follows OS-level selection conventions that every developer already knows. The floating batch action bar at the bottom is a well-established pattern from Gmail, Linear, and macOS Finder.
- **Conditions**: (1) The context menu must be keyboard-accessible: Space or Shift+F10 on a focused card must open it, and arrow keys must navigate within it. Do not rely solely on right-click. (2) The floating batch action bar must not obscure the board content below it -- use a semi-transparent background or offset it so the last row of cards remains visible. (3) Batch operations must show a progress indicator that survives if the user scrolls or navigates -- do not use auto-dismissing toasts for multi-step operations. A persistent progress bar or inline status is better.

## power-recent-activity-and-quick-switch.md
- **Verdict**: APPROVE
- **Reasoning**: The sidebar currently shows only three static links (Home, Board, Settings) and provides no reflection of the user's actual work context. Adding a "Recent" section with the last 8 visited issues transforms the sidebar from a static menu into a contextual navigation hub. The Ctrl+Tab quick-switch interaction directly maps to the OS-level and browser-level window/tab switching pattern that developers use hundreds of times per day. The activity indicator dots (blue for active chat, green for uncommitted changes) add information density without adding clutter.
- **Conditions**: (1) The "Recent" section in the sidebar must be collapsible so users with smaller screens or who prefer a minimal sidebar can hide it. (2) The Ctrl+Tab quick-switch overlay must handle the edge case where Ctrl is released very quickly (within 100ms of Tab) -- in that case, it should switch to the most recent item immediately rather than showing and immediately hiding the overlay, which would cause visual flicker. (3) The status indicator dots must have tooltips explaining what they mean ("Active chat session" / "Uncommitted changes") since color alone is insufficient for colorblind users.
