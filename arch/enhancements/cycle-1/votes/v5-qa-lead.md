# Votes: QA Lead

## growth-contextual-empty-states.md
- **Verdict**: APPROVE
- **Reasoning**: Empty states are purely additive presentational components with no side effects on existing logic. The existing test suite already covers the board column derivation, chat MessageList empty state rendering, and IDE component rendering -- each new empty state component can be tested in isolation with straightforward render assertions. The blast radius is minimal: conditional rendering inserted into existing views only activates when data is absent, so existing happy-path tests remain unaffected.
- **Conditions**: Each empty state component (BoardEmptyState, ChatWelcome, IDEEmptyState, SetupChecklist) must have its own unit test verifying render output and CTA button callbacks. Integration tests for BoardView, ChatView, and IDELayout must be updated to assert that the empty state renders when config/data is null and does NOT render when valid data is present. Verify that the existing ErrorBoundary tests still pass and that error states remain distinguishable from empty states.

## growth-interactive-playground.md
- **Verdict**: APPROVE
- **Reasoning**: The playground is well-isolated behind a dedicated `/playground` route and uses static fixture data, so it cannot regress authenticated flows. The key testability concern -- that existing components will accept `staticData` / `demoMessages` / `staticFiles` props -- is mitigable by ensuring the new prop paths are guarded and the default (no prop) path is untouched. The existing MSW mock infrastructure already provides a model for fixture-based testing.
- **Conditions**: Fixture data must have a dedicated test file validating its schema matches the types expected by BoardView, ChatView, and IDELayout (prevents silent breakage when types evolve). The playground route must have integration tests verifying all three views render with static data. Regression tests must assert that when static data props are undefined, existing TanStack Query / VFS fetch behavior is unchanged. The "playground vs real data" confusion risk should be verified by testing banner visibility.

## growth-keyboard-shortcuts-command-palette.md
- **Verdict**: REJECT
- **Reasoning**: This proposal is a superset that duplicates two other proposals in the same cycle (power-command-palette.md and power-keyboard-shortcuts.md). Approving this alongside those creates ambiguity about which specification to implement and test against. The scope is also very broad -- combining a command palette, 30+ shortcuts across 4 contexts, a help overlay, and a command registry in a single proposal makes it difficult to write precise acceptance criteria and isolate failures during testing.
- **Conditions**: N/A. Recommend consolidating with power-command-palette.md and power-keyboard-shortcuts.md into a single canonical proposal with phased delivery, or withdrawing this one in favor of the two more focused proposals.

## growth-progressive-auth-nudges.md
- **Verdict**: APPROVE
- **Reasoning**: The proposal is testable with clear acceptance criteria: inline prompts render in specific conditions (no provider configured, no Jira auth, no GitHub auth), Ollama detection returns a result, and auth redirect preserves the return URL. The existing AuthManager test suite (manager.test.ts) already covers token set/get/expiry/disconnect and provides a solid foundation for testing the new `setPendingRedirect`/`consumePendingRedirect` methods. The blast radius is moderate -- it modifies ChatView, BoardView, and IDELayout -- but each change is a conditional branch that only activates when auth is missing.
- **Conditions**: The Ollama localhost detection must be tested with both success and failure (CORS block, timeout, Ollama not running) scenarios. The `setPendingRedirect`/`consumePendingRedirect` pair must have unit tests in manager.test.ts covering set-then-consume, consume-without-set (returns null), and sessionStorage persistence across page reload simulation. Each inline auth prompt component must have render tests. The existing ProviderPicker dialog must remain accessible via "More options" and its existing test coverage must not regress.

## growth-shareable-deep-links.md
- **Verdict**: APPROVE
- **Reasoning**: Deep links are highly testable because they are deterministic: given URL params, the app must initialize specific state. The existing test infrastructure (TanStack Router setup in app.test.tsx, board store filter tests in board-flow.test.tsx) provides the patterns needed. The URL schema is simple and the risk of regression is low because each feature (board filter params, chat message anchors, IDE file params) is additive.
- **Conditions**: Board filter serialization/deserialization must have unit tests for round-trip fidelity (serialize filters to URL params, then parse back and verify equality). Edge cases to test: malformed params (graceful fallback to defaults), missing params (no filter applied), URL-encoded special characters in filter values. Chat message anchor scrolling must be tested with both valid and invalid message IDs. IDE file+line params must be tested with files that do not exist in the tree (graceful fallback). The auth redirect preservation shares implementation with growth-progressive-auth-nudges -- coordinate to avoid duplication.

## platform-cache-eviction-and-quota.md
- **Verdict**: APPROVE
- **Reasoning**: The existing CacheStore test suite (indexeddb.test.ts) already covers set/get/has/delete/clear/evictExpired with a thorough in-memory IndexedDB mock, providing an excellent foundation. The eviction scheduler and quota manager are testable with fake timers and deterministic data. The main risk is browser-specific quota behavior (Safari vs Chrome vs Firefox), but the proposal correctly relies on `navigator.storage.estimate()` which can be mocked in tests.
- **Conditions**: The eviction scheduler must be tested with vi.useFakeTimers for the 15-minute interval trigger, visibility-change trigger, and startup trigger. QuotaExceededError handling in CacheStore.set() must be tested by mocking the IDB put to throw. LRU eviction must be tested by inserting entries with known timestamps and verifying the oldest entries are evicted first. The `getEntryCount()` and `getOldestEntries(n)` new methods on CacheStore need unit tests. The Settings storage panel UI needs render tests. `navigator.storage.estimate()` must be mocked for the usage display tests.

## platform-llm-context-budget.md
- **Verdict**: APPROVE
- **Reasoning**: The token budget calculator and compaction strategies are pure functions that are straightforward to unit test. The existing system-prompt.test.ts and stream-parser.test.ts suites demonstrate the pattern for testing LLM infrastructure. The key regression risk is in the chat store (stores/chat.ts) where compaction modifies the message array -- but the existing chat store tests (session creation, message ordering, model switching) provide a safety net.
- **Conditions**: The token estimator must be tested against known strings with expected token counts (within the stated 10% margin). Compaction phase 1 (tool result pruning) must be tested by creating a session with old tool results and verifying they are replaced with summaries. Compaction phase 3 (hard truncation) must verify that the system prompt and last 10 messages are always preserved. The `context_overflow` chunk type in stream-parser must be tested for both Anthropic and OpenAI error formats. The context usage indicator UI must be tested for correct display at 0%, 50%, 75%, and 100% budget usage. Edge case: empty conversation should show 0 tokens used.

## platform-offline-resilience.md
- **Verdict**: APPROVE
- **Reasoning**: The proposal is well-structured for testing: TanStack Query configuration changes are verifiable through query behavior tests, the mutation queue is an IndexedDB-backed data structure with FIFO semantics that is straightforward to unit test, and the online/offline indicator is a simple derived state. The existing board-flow integration tests and VFS tests provide regression coverage for the read paths. The main risk is the mutation queue's idempotency requirements, but the proposal acknowledges this and specifies conflict detection.
- **Conditions**: The mutation queue must be tested for: enqueue while offline, drain on online transition, retry with exponential backoff (using fake timers), max retry exhaustion, manual discard, and FIFO ordering. `navigator.onLine` must be mockable in tests. The stale-while-revalidate behavior must be tested by: loading data, going offline, and verifying cached data is returned without error. Optimistic update persistence to IndexedDB must be tested for survive-refresh semantics. The ConnectionIndicator must be tested for all three states (online, degraded, offline). Edge case: rapid online/offline toggling must not cause duplicate mutation execution.

## platform-resilient-api-fetch.md
- **Verdict**: APPROVE
- **Reasoning**: This is a single-file utility module (~150 lines) with clear, testable behavior: retry on specific status codes, exponential backoff with jitter, rate-limit header parsing, request deduplication, and abort signal propagation. The existing JiraClient and GitHubClient test suites (client.test.ts for both) mock `fetch` directly and provide the integration pattern. The blast radius is narrow -- only two call sites (JiraClient.request, GitHubClient's internal fetch) are modified.
- **Conditions**: Unit tests for resilient-fetch.ts must cover: retry on each retryable status (429, 500, 502, 503, 504), no retry on non-retryable status (400, 401, 403, 404), exponential backoff timing (with fake timers), Retry-After header parsing (both seconds and HTTP-date formats), GET deduplication (two concurrent identical GETs return the same promise), POST non-deduplication, abort signal cancellation mid-retry, and max retry exhaustion. The jitter must be seeded or bounded for deterministic tests. Integration tests must verify JiraClient and GitHubClient use resilientFetch by checking that a 503 is retried automatically.

## platform-structured-error-recovery.md
- **Verdict**: APPROVE
- **Reasoning**: The error classifier is a pure function mapping HTTP status codes and error types to an enum -- highly testable. The existing ErrorBoundary test (components.test.tsx) and toast test (board.test.tsx) provide the foundation for verifying the enhanced toast behavior (persistent flag, action buttons). The auth-expired interceptor is the highest-risk piece, as it pauses and replays requests, but this is testable with mock fetch and fake timers.
- **Conditions**: The error classifier must have exhaustive tests mapping each HTTP status code to the correct ErrorCategory. The toast store extension must be tested for: persistent toasts do not auto-dismiss, action buttons render and fire callbacks, error history accumulates up to 20 entries, and oldest entries are evicted beyond 20. The auth-expired interceptor must be tested for: detecting 401, pausing subsequent requests, showing re-auth prompt, and replaying paused requests on success. Edge case: re-auth failure must drain the queue with errors, not retry forever. The existing ErrorBoundary and toast auto-dismiss tests must continue to pass.

## power-command-palette.md
- **Verdict**: APPROVE
- **Reasoning**: This proposal is well-scoped: a single new component (CommandPalette.tsx), a thin store (palette.ts), and a global keydown listener. The three input modes (issue search, file search, command mode) are deterministic given the data in Zustand stores and can be tested with the existing pattern of rendering components and firing keyboard events. The Monaco focus collision risk is explicitly addressed with a mitigation strategy.
- **Conditions**: Unit tests must cover: opening via Cmd+K keydown, closing via Escape, fuzzy search filtering (exact match, partial match, no match), mode detection (default, `>` prefix, `/` prefix), result selection via Enter, keyboard navigation with arrow keys, and recency ranking (recently selected items appear first). The fuzzy match utility function must have its own unit tests with edge cases (empty query, special characters, very long strings). Integration test: verify the palette does NOT open when a Monaco editor has focus and Cmd+K is pressed. The palette must not interfere with existing chat MessageInput Enter handling.

## power-keyboard-shortcuts.md
- **Verdict**: APPROVE
- **Reasoning**: The proposal defines a clear, layered shortcut system with well-defined scopes (global, board, chat, IDE). Each shortcut maps to a specific store action or router navigation, making tests deterministic: fire a keydown event, assert the corresponding action was called. The guard logic (suppress single-key shortcuts in text inputs) is a well-understood pattern that is easy to test. The existing board store (useBoardStore) already has the infrastructure for testing new actions like `focusNextCard`.
- **Conditions**: Each shortcut must have a test verifying: (1) the action fires on the correct key combination, (2) the action does NOT fire when a text input has focus (for single-key shortcuts without modifiers), (3) the action does NOT fire when the wrong view/scope is active. The `focusedCardIndex` board store field must be tested for boundary conditions: focus at first card pressing up, focus at last card pressing down, focus on an empty column. `Cmd+W` (close tab) must be tested to verify it does NOT close the browser tab (i.e., `preventDefault` is called). The shortcuts help overlay (`?`) must render the correct shortcuts for each context.

## power-quick-issue-actions.md
- **Verdict**: APPROVE
- **Reasoning**: The proposal has three distinct parts with increasing complexity. Part 1 (context menu) is low-risk using Radix ContextMenu which is already in the dependency tree. Part 2 (multi-select) adds state management to the board store that is testable but introduces the highest regression risk since it modifies Card and Column rendering. Part 3 (hover icons) is pure CSS with click handlers. The new Jira client methods (assignIssue, setPriority, addLabel) follow the same pattern as existing doTransition and are easily testable with the existing mock fetch infrastructure.
- **Conditions**: Context menu must be tested for: right-click opens menu, each action calls the correct Jira API method, menu closes after action. Multi-select must be tested for: Cmd+click toggles selection, Shift+click selects range, clearing selection, batch action progress, and batch action with mixed success/failure. New Jira client methods must have unit tests in client.test.ts following the existing doTransition test pattern. Edge cases: selecting cards across columns, batch transition when one card has already been transitioned (conflict), and context menu on a card that has been optimistically updated. The existing board-flow integration tests must not regress.

## power-recent-activity-and-quick-switch.md
- **Verdict**: APPROVE
- **Reasoning**: The activity store is a simple list data structure (max 20 entries, persisted to localStorage) that is straightforward to unit test. The sidebar "Recent" section is a render-only addition to an existing component. The quick-switch overlay (Ctrl+Tab) is the most complex piece but follows a well-known interaction pattern. The status indicator dots derive from existing store state (chat sessions, VFS changes) with no new API calls, keeping the blast radius contained.
- **Conditions**: The activity store must be tested for: adding a visit, deduplication by issue key, max 20 entry cap, most-recent-first ordering, and localStorage persistence/restoration. The sidebar "Recent" section must be tested for: rendering up to 8 items, correct issue key and summary display, navigation on click, and status dot derivation (blue dot for active chat, green dot for uncommitted changes, no dot for idle). The quick-switch panel must be tested for: Ctrl+Tab opens panel, subsequent Tab cycles highlight, Ctrl release navigates to highlighted item, and Escape dismisses. Edge case: quick-switch with only 1 recent item, quick-switch with 0 recent items (should not open).
